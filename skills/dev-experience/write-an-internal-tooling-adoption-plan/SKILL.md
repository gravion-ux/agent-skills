# Plan internal tooling adoption with target users, migration steps, enablement, and measurable outcomes

## Purpose

Plan internal tooling adoption with target users, migration steps, enablement, and measurable outcomes.

## When to use

Use when the user wants teams to adopt a new internal developer tool successfully.

## When NOT to use

Do not use this for a one-off local script; use software-engineering instead.

## Inputs required

- The recurring friction the team hits
- Who experiences it and how often
- The tooling already in place

## Procedure

1. Identify target users, current workflows, and the friction the tool removes.
2. Define a pilot cohort, baseline measures, and explicit adoption success criteria.
3. Prepare migration instructions, support channels, and reversible fallback steps.
4. Schedule enablement that uses each team's existing tools and examples.
5. Review pilot results, address blockers, and publish the rollout decision.

## Output contract

A working tool, template or command plus the documentation and adoption note.

## Validation checklist

- [ ] The friction is measured before and after
- [ ] The new path is documented and discoverable
- [ ] It does not add a step to the critical path

## Safety notes

Never change a shared default that silently affects every developer without a migration note.
