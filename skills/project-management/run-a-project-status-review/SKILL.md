# Run a project status review grounded in delivered work, current dependencies, and next decisions

## Purpose

Run a project status review grounded in delivered work, current dependencies, and next decisions.

## When to use

Use when the user needs to assess project health and coordinate decisions across contributors.

## When NOT to use

Do not use this for the technical design of the work; use architecture-design instead.

## Inputs required

- The goal, deadline and constraints
- The people and their capacity
- The dependencies outside the team's control

## Procedure

1. Ask each workstream owner for completed evidence, current blockers, and next commitment.
2. Reconcile updates with the plan and mark tasks complete only from delivered artefacts.
3. Surface missing owners, blocked dependencies, and overdue commitments.
4. Assign each blocker or decision to one owner and a resolution date.
5. Publish the current status, material changes, and next review date.

## Output contract

A plan with milestones, owners, dependencies, risks and a status view that stays true.

## Validation checklist

- [ ] Every task has one owner
- [ ] Dependencies and blockers are visible
- [ ] The plan reflects actual status, not the original estimate

## Safety notes

Never report progress that is not backed by delivered work.
