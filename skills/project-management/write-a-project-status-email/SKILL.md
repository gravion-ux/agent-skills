# Write a concise project status email that separates delivered results, current blockers, and requested decisions

## Purpose

Write a concise project status email that separates delivered results, current blockers, and requested decisions.

## When to use

Use when the user needs to update stakeholders on project delivery without overstating progress.

## When NOT to use

Do not use this for the technical design of the work; use architecture-design instead.

## Inputs required

- The goal, deadline and constraints
- The people and their capacity
- The dependencies outside the team's control

## Procedure

1. List completed deliverables with links or other evidence and confirm their acceptance status.
2. State current status against committed milestones, dates, and the latest baseline.
3. Summarize active dependencies, blockers, risks, and their accountable owners.
4. Request specific decisions or actions with deadlines and recipients.
5. Include the next checkpoint and avoid claims unsupported by delivered work.

## Output contract

A plan with milestones, owners, dependencies, risks and a status view that stays true.

## Validation checklist

- [ ] Every task has one owner
- [ ] Dependencies and blockers are visible
- [ ] The plan reflects actual status, not the original estimate

## Safety notes

Never report progress that is not backed by delivered work.
