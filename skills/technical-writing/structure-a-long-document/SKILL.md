# Structure a long document so the reader can find the part they need without reading it all

## Purpose

Structure a long document so the reader can find the part they need without reading it all.

## When to use

Use when the user has a lot of material and needs it organised into a usable document.

## When NOT to use

Do not use this for a reference-manual API listing; use api-design instead.

## Inputs required

- The technical subject and the reader's level
- The decision the reader must make
- The evidence and examples available

## Procedure

1. Write the sections the reader will look for before writing the prose.
2. Give each section one job and move anything else to its own section.
3. Put the summary and the decision at the top, not the context.
4. Add a table of contents that names the sections by what they answer.
5. Check that no section is long enough to need splitting into two.

## Output contract

A precise technical document with a clear structure, correct terminology and verified examples.

## Validation checklist

- [ ] The terminology is consistent throughout
- [ ] Every instruction was followed once end to end
- [ ] The document states its assumptions

## Safety notes

Never state a performance, security or compatibility claim that was not verified.
