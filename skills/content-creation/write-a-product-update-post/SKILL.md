# Turn release notes into a product update post that states what changed and why

## Purpose

Turn release notes into a product update post that states what changed and why.

## When to use

Use when the user wants to announce a product change to existing users.

## When NOT to use

Do not use this for internal engineering documentation; use technical-writing instead.

## Inputs required

- The platform and the format
- The audience and the tone
- The source material, the hook and the call to action

## Procedure

1. Group the release notes into new, improved and fixed changes.
2. Lead with the user-facing benefit instead of internal ticket names.
3. Link each change to the feature it affects and add a screenshot where useful.
4. Note any action users must take and the deadline if one applies.
5. Close with a short line on what comes next and leave approval pending.

## Output contract

A publishable draft in the target format, with a title, hook, body and close.

## Validation checklist

- [ ] The opening earns the next sentence
- [ ] The draft matches the platform's format and length
- [ ] Every factual claim is sourced

## Safety notes

Never publish without approval, and never present generated statistics as real data.
