# Explain a release's user-visible changes, impact, and required action in plain language

## Purpose

Explain a release's user-visible changes, impact, and required action in plain language.

## When to use

Use when the user wants release notes that tell customers what changed and what to do.

## When NOT to use

Do not use this for a persuasive article or campaign copy; use content-creation instead.

## Inputs required

- The audience and what they must be able to do
- The subject and the source material
- The format and the maintenance owner

## Procedure

1. Identify the release version and publication date.
2. List user-visible improvements, fixes, and breaking changes.
3. Mark actions that users must complete before upgrading.
4. Link each claim to the matching changelog entry.
5. Check the notes against the actual release contents.

## Output contract

A document that answers the reader's question, with structure, examples and an owner.

## Validation checklist

- [ ] The document answers its stated question
- [ ] Examples are runnable and current
- [ ] Every claim can be traced to a source

## Safety notes

Never document a command you have not run, and never leave an internal secret in an example.
